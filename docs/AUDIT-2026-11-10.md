### Parcours comptoir — comptage des taps (OBSERVÉ depuis le code)

Client nouveau, visite du jour, caisse déjà déverrouillée : **~7–8 taps + 1 saisie** (scan QR → inscription 2 taps + saisie → caisse 3 taps → « Tourner la roue » 1 tap → « Voir ma carte » 1 tap), mais 2 allers-retours téléphone↔comptoir, ~10 s d'attente de déblocage + 4,5 s de rotation → **~30–45 s réelles, hors file d'attente**. Caisse verrouillée : +5 taps. Client connu : inscription = 1 tap (« Continuer en tant que… »).

### Ce qui est bon (à ne pas casser)

- Boutons/champs ≥ 44 px presque partout, `min-h-12`, `viewport-fit=cover` + `safe-area-inset-bottom`.
- États vides soignés sur tous les écrans, messages d'erreur clairs (`role="alert"`), jamais de faux résultat.
- Hors-ligne caisse robuste : file d'attente, pas de double comptage.
- Vouvoiement constant, français intégral, contrastes principaux ≥ 4,5:1.
- Tirage entièrement décidé serveur ; lot jamais accepté du navigateur ; index unique 1 tirage/jour (Supabase) + contrainte unique inscription.
- Validation d'entrées systématique, listes blanches de champs, corps limités, `Cache-Control: no-store`, erreurs 500 génériques, PIN/hash jamais renvoyés, codes équipe jamais journalisés.
- RLS : activée partout, zéro policy, `anon`/`authenticated` révoqués ; clé service_role côté serveur uniquement.
- Aucun secret en dur dans le code actuel ; `.env` ignoré ; `render.yaml` sans valeur secrète.
